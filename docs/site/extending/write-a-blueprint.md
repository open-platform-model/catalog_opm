<!-- One sentence: this adds a new blueprint (a named composition of resources and traits, such as a stateless workload) to a catalog, so that module authors can start a component from one line and write its settings under one key. The reader needs it when the same combination of resources and traits recurs across modules and no blueprint in the catalog composes it. Say that a blueprint renders nothing itself: the transformers that handle its resources and traits render the component, selected by the matching label the blueprint answers. Say that nothing can demand a blueprint, so it has no fulfilment and no transformer of its own; a blueprint that needs a new workload type also needs a transformer, "Write a transformer". Check against: core/src/blueprint.cue, core/SPEC.md section 3.3, catalog_opm/src/blueprints/v1beta1/stateless_workload.cue, catalog_opm/docs/site/authoring/choose-a-blueprint.md -->

## Before you begin

<!-- The reader must already have: a catalog to add the blueprint to, either a checkout of catalog_opm or their own catalog module (cue.mod/module.cue, identity/identity.cue and a catalog.cue that embeds core's #Catalog); every resource and trait the blueprint composes, defined and listed in that catalog (see "Write a resource" and "Write a trait"); the cue CLI at the version the catalog builds with (catalog_opm CI pins v0.17.1; Verify: the minimum version a reader needs); the opm CLI for the publish dry run; registry access, with CUE_REGISTRY and OPM_REGISTRY set as the catalog's AGENTS.md says, because cue resolves core from the registry and every command below fails without it. The reader has read the concept page "Components and blueprints". Verify: that a trait from a foreign catalog module attached beside a blueprint's wrapper still fails with "field not allowed" on current core and cue v0.17.1 (measured only on the retired experimental catalog, when core closed spec at component.cue:80; the close() now sits at :224), and whether a blueprint can compose a trait from another catalog module. Check against: catalog_opm/.github/workflows/ci.yml, catalog_opm/AGENTS.md (Dependencies), catalog_opm/src/catalog.cue, catalog_opm/src/blueprints/v1beta1/network_policy_attachment.cue, core/src/component.cue (spec) -->

## Steps

<!-- The steps edit CUE files in the catalog source. The running example is stateless-workload: it composes one resource and five traits, answers the container resource's required workload-type key, and propagates each composed field with its guard at component level. stateful-workload is the example for a name constraint. Steps 5 and 6 apply only when their condition holds, the label in step 7 only when step 5 applies, and step 12 only to catalog_opm; the step names say so. -->

1. File the blueprint under its apiVersion.
   <!-- The file goes in <module>/blueprints/<apiVersion>/<name>.cue with the package clause equal to the version segment (package v1beta1). The segment never enters the fqn. Publish's member gate refuses a blueprint whose modulePath is flat or names a segment other than its apiVersion; nothing checks that the directory it sits in matches. The contract levels are the same as for a resource: if the shape may still change, file it at v1alpha1, where alpha promises nothing; beta and GA members are additive-only. catalog_opm's five blueprints sit in src/blueprints/v1beta1/, and no blueprints/v1alpha1 directory exists yet, so a blueprint filed at alpha needs that directory and its own import alias in catalog.cue, grouped last. network_policy_attachment.cue in the v1beta1 directory is a test file, not a blueprint. Check against: catalog_opm/AGENTS.md (Version-segment filing, Listing), core/SPEC.md section 3.3 Constraints, core/src/identity_package.cue (declaredModulePath), cli/internal/publish/catalog_gates.go (gateMemberFQN), cli/internal/publish/members.go (memberPackagePaths, membersOfPackage), catalog_opm/docs/site/reference/catalog-contract.md (Contract levels), catalog_opm/src/catalog.cue -->
2. Declare the blueprint's identity.
   <!-- Show #<Name>Blueprint: c.#Blueprint & {metadata: {...}} with modulePath "\(id.kindPrefix.blueprints)/<apiVersion>", name in kebab case (stateless-workload), apiVersion, catalogVersion: id.Version, fqn "\(id.kindPrefix.blueprints)/<name>@<apiVersion>" and a one-line description. Write fqn with the interpolation on one line: task vet:listing builds the set of members it expects by grepping for that form. description is optional in core, but every catalog blueprint sets one. labels and annotations are optional and only describe; the five catalog blueprints set none. Never add fulfilment: nothing can demand a blueprint, and the closed definition refuses the field with "field not allowed". As for a resource, an fqn that disagrees with name or apiVersion passes cue vet and is refused by publish's member gate. Check against: core/src/blueprint.cue (metadata, the comment on fulfilment above composedResources), core/src/identity_package.cue (#CatalogMemberFQNGate), catalog_opm/src/identity/identity.cue (kindPrefix), catalog_opm/.tasks/listing.sh, catalog_opm/src/blueprints/v1beta1/stateless_workload.cue -->
3. List what the blueprint composes.
   <!-- composedResources lists the resources by definition ([res.#ContainerResource]); the stateful blueprint adds res.#VolumesResource. composedTraits lists the traits (tr.#ScalingTrait, tr.#RestartPolicyTrait, tr.#UpdateStrategyTrait, tr.#SidecarContainersTrait, tr.#InitContainersTrait). composedResources is required; composedTraits is optional. For spec and rendering the lists are references only: the fields a module writes come from the schema (step 4), and the component carries the primitives because the wrapper embeds them (step 7). They are still contract surface: at beta or GA, publish's compatibility gate compares both lists, element by element while their lengths match (a change inside a composed member is reported at composedResources[i]) and as one value when a length changes, so a change to a composed member, or to the list itself, is judged like a change to the blueprint's own schema. Verify: whether appending to composedTraits of a published v1beta1 blueprint is refused. Verify: core/SPEC.md section 3.3 says composedResources must list at least one resource and that each composed trait must have a composed resource in its appliesTo, but core/src/blueprint.cue types the list as [...#Resource] and core/src/component.cue never reads appliesTo, so state both as requirements without naming a check. Check against: core/src/blueprint.cue (composedResources, composedTraits), core/SPEC.md section 3.3 Constraints, cli/internal/compat/compat.go (walkList), cli/internal/compat/compat_test.go (TestCheckMemberReferencesStillReportRealChanges), catalog_opm/src/blueprints/v1beta1/stateless_workload.cue, catalog_opm/src/blueprints/v1beta1/stateful_workload.cue -->
4. Write the schema under the blueprint's key.
   <!-- A separate #<Name>Schema in the same file reuses the schemas of what the blueprint composes: container: res.#ContainerSchema is required (no ?), and each composed trait is optional (scaling?: tr.#ScalingSchema; list-valued traits as sidecarContainers?: [...tr.#SidecarContainersSchema]). The blueprint's spec has exactly one field, named after it in camel case (stateless-workload becomes statelessWorkload), holding that schema: spec: statelessWorkload: #StatelessWorkloadSchema. Module authors write every setting under that key, composed traits included. The wrapper's embeds (step 7) admit each composed field at spec level as a schema; only the propagation line (step 8) gives it the module's value. That is why a propagation line is allowed in the closed spec, and also why a module could write spec.scaling directly, beside the blueprint's key. Check against: core/src/blueprint.cue (spec!), core/src/component.cue (_allFields, spec), core/SPEC.md section 3.3 Constraints, catalog_opm/src/blueprints/v1beta1/stateless_workload.cue (#StatelessWorkloadSchema), catalog_opm/docs/site/authoring/choose-a-blueprint.md -->
5. If a composed resource declares a required matching key, answer it.
   <!-- Answer every required matchLabels key a composed resource declares, with matchLabels on the blueprint. In catalog_opm only the container resource declares one, "core.opmodel.dev/workload-type", with the values stateless, stateful, daemon, task and scheduled-task: a blueprint that composes it sets matchLabels: "core.opmodel.dev/workload-type": "<value>". Core types a blueprint's matchLabels as optional, so a blueprint that composes no such resource sets none. Attaching the blueprint answers the key and completes the component's matching identity, and the workload transformer whose requiredLabels carry the same value renders the component (the deployment transformer requires stateless, the daemonset transformer daemon, the cronjob transformer scheduled-task); "How matching works" explains the selection. Forks as conditions: if the blueprint renders to an existing workload kind, reuse its value and the existing transformers select it. If it needs a new kind, and only inside catalog_opm, add the value to the container's enum in both places it appears (the resource's matchLabels and the #Container wrapper's metadata.labels) and write a transformer that requires it, following "Write a transformer"; adding an option to a disjunction is additive under the Catalog Contract. A blueprint in another catalog that composes the container resource cannot edit container.cue and must answer one of the existing values. Verify: what each transformer that reads the value does with a new one (the hpa transformer falls back to Deployment for any value but stateful). Check against: catalog_opm/src/resources/v1beta1/container.cue, core/src/blueprint.cue (matchLabels), core/src/component.cue (_matchLabelsFromPrimitives), catalog_opm/docs/site/reference/catalog-contract.md (The additive-only rule), catalog_opm/src/transformers/deployment_transformer.cue, catalog_opm/src/transformers/daemonset_transformer.cue, catalog_opm/src/transformers/cronjob_transformer.cue, catalog_opm/src/transformers/hpa_transformer.cue (_kind) -->
6. If the rendered workload's name is a DNS label, make sure a name constraint covers it.
   <!-- The #Container wrapper already puts c.#NameType on the container entry when the component's derived matchLabels read workload-type stateful, and that rule resolves on the blueprint path, because it reads the component's matchLabels rather than the entry's own key. So a blueprint that answers stateful is covered already: a blueprint-level #nameConstraint: c.#NameType, as the stateful blueprint declares, is harmless but redundant (measured, cue v0.17.1: with the stateful blueprint's slot removed, a 64-rune resourceName is still refused by strings.MaxRunes(63)). core/SPEC.md section 3.3 also calls it redundant. stateful_workload.cue's own comment, which calls its constraint load-bearing because the container's conditional cannot fire, describes the older entry-level form of that conditional. If the blueprint answers a new workload-type value that renders a kind whose name is a DNS label, declare #nameConstraint: c.#NameType on the blueprint (or, in catalog_opm, extend the wrapper's conditional). Otherwise leave it alone: the default accepts any name. Never guard on the slot's presence. Check against: catalog_opm/src/resources/v1beta1/container.cue (the WHY block on #Container), catalog_opm/docs/name-constraints.md (A computed constraint must resolve on every attachment path), catalog_opm/src/blueprints/v1beta1/stateful_workload.cue, core/src/blueprint.cue (#nameConstraint), core/SPEC.md section 3.3 Constraints -->
7. Add the component wrapper.
   <!-- #<Name>: c.#Component & {...} beside the blueprint. It attaches the blueprint as #blueprints: (#<Name>Blueprint.metadata.fqn): #<Name>Blueprint and embeds the wrapper of every composed resource and trait (res.#Container, tr.#Scaling, tr.#RestartPolicy, and so on). If the blueprint composes the container resource, the wrapper also sets metadata: labels: "core.opmodel.dev/workload-type": "<value>", and the label is not optional: the #Container wrapper declares that metadata label as required, and the hpa transformer reads the workload type from metadata.labels, not from matchLabels. The blueprint's own comment calls the label a transitional duplicate until the kernel's matcher reads only matchLabels; that comment is out of date, because the matcher already compares matchLabels only, and the two reasons above are why the label stays. Module authors embed this wrapper (bp.#StatelessWorkload), never the blueprint itself. Check against: catalog_opm/src/blueprints/v1beta1/stateless_workload.cue (#StatelessWorkload), catalog_opm/src/resources/v1beta1/container.cue (#Container), catalog_opm/src/transformers/hpa_transformer.cue (_workloadType), library/opm/internal/renderstage/render.cue.tmpl (rung 3, missingLabels), catalog_opm/docs/site/authoring/choose-a-blueprint.md -->
8. Propagate the schema to the fields the transformers read.
   <!-- Transformers read spec.container, spec.scaling and the other flat fields, never spec.<camelName>. In the wrapper, re-declare spec with the blueprint's key and copy each required field: spec: {statelessWorkload: #StatelessWorkloadSchema, container: spec.statelessWorkload.container}. Copy each optional field with a guard at component level, outside the spec block: if spec.statelessWorkload.scaling != _|_ {spec: scaling: spec.statelessWorkload.scaling}. The wrong form puts that guard inside spec: {...}; for a struct- or list-valued field, cue rejects it with "field not allowed" (an evaluator regression from v0.17.0-alpha.2, still present in v0.17.1), so the hoisted form is load-bearing and must not be tidied away. Every schema field needs a propagation line, or a module's value is accepted and never reaches a transformer. Verify: #StatelessWorkloadSchema also carries securityContext, hostPid and hostIpc, which the blueprint does not compose, the wrapper does not propagate and no transformer reads under statelessWorkload; confirm whether that is a bug before pointing at the file as the model for this step. Check against: catalog_opm/src/blueprints/v1beta1/stateless_workload.cue, catalog_opm/docs/cue-guard-closedness-workaround.md, catalog_opm/AGENTS.md (Repository Rules, CUE authoring pitfall), core/src/component.cue (_allFields, spec) -->
9. Write the doc comment.
   <!-- A new catalog member must ship a doc comment directly above #<Name>Blueprint: what it composes, what it renders to, what a value must satisfy, at most 6 lines. Rationale goes in a // WHY block above it, separated by one blank line. The generated INDEX.md takes the comment's first sentence, up to the first period, as the member's description. The five shipped blueprints carry no doc comment above the definition and show a blank description in INDEX.md; do not copy them. task docs:check fails a comment over 6 lines. Verify: catalog CI does not yet refuse a member with no doc comment (today it checks length only); state the rule as a requirement without naming a gate unless one has shipped. Check against: catalog_opm/AGENTS.md (Doc comments), catalog_opm/.tasks/doc-check.sh, catalog_opm/.tasks/generate-index.sh (extract_definitions), catalog_opm/src/INDEX.md -->
10. List the blueprint in the catalog manifest.
    <!-- Add (bp.#<Name>Blueprint.metadata.fqn): bp.#<Name>Blueprint to the #blueprints map in catalog.cue, keyed by the fqn reference and never by a string literal, in alphabetical order. The value is the blueprint, not the wrapper: the wrapper declares no fqn and is not a member. The catalog stamps modulePath and catalogVersion on every entry, and a disagreeing authored value is a conflict. Check against: catalog_opm/src/catalog.cue, core/src/catalog.cue (#blueprints), catalog_opm/.tasks/listing.sh, catalog_opm/AGENTS.md (Listing) -->
11. Add fixtures that build a component from the wrapper.
    <!-- In the blueprint's own package, not in transformers/ (transformers do not import blueprints, and should not start): _test<Name>: #<Name> & {metadata: name: "...", spec: <camelName>: {container: {...}, ...}}, setting each composed trait under spec.<camelName>. For each propagation line, pin the value as it arrives at the flat field with a guard that forces evaluation: _test<Name>Scaled: (_test<Name>.spec.scaling.count + 0) & 3. Such a guard proves the propagation only under cue eval -c -e <guard> or cue export -e <guard>: with the propagation line missing, the wrapper's embeds still give the flat field its schema, so the guard is only incomplete, and cue vet, with or without -c, exits 0 (measured, cue v0.17.1, stateless-workload with its scaling line removed: eval -c fails with "non-concrete value >=0 & <=1000 & int in operand to +"). A length guard on a list-valued field, (len(x.spec.sidecarContainers) + 0) & 1, also fails plain cue vet, because an unfilled open list has length 0; that is why network_policy_attachment.cue's attachment guards work under vet. Pin what must not arrive with [if ... != _|_ {"leaked"}] & []. If a trait the blueprint does not compose must be attachable beside it, add an attachment fixture as network_policy_attachment.cue does for stateless and daemon. No task runs blueprint fixtures today: task vet:fixtures selects only fields declared _test<Name>: (#<Transformer>.#transform & { under transformers/. Check against: catalog_opm/src/blueprints/v1beta1/network_policy_attachment.cue, catalog_opm/src/transformers/network_policy_transformer.cue (the comment on the blueprint-attachment test), catalog_opm/.tasks/fixtures.sh, catalog_opm/docs/name-constraints.md (Fixtures that exercise a wrapper default) -->
12. In catalog_opm, regenerate the index and run the checks.
    <!-- task generate:index regenerates src/INDEX.md, which lists the blueprint, its wrapper and its schema; task check runs format, vet, listing, fixtures, index freshness and the doc-comment limit. task fmt:check diffs the git index, so stage the edits first. A new blueprint lands as a feat: commit, a minor release. Check against: catalog_opm/Taskfile.yml, catalog_opm/AGENTS.md (Build And Dev Commands, Commit conventions and release impact), catalog_opm/src/INDEX.md -->

## Check that it worked

<!-- One command, from the catalog module directory, run once per propagation guard from step 11: cue eval -c -e _test<Name><Field> ./blueprints/<apiVersion>. Success is each pinned value printed (3 for the scaling guard above). Say that plain cue vet ./blueprints/<apiVersion> catches only conflicts (a field that is not allowed, a wrong concrete value, a list whose length disagrees), not a missing propagation line, which leaves a scalar guard incomplete and vet exiting 0. Say that publish's dry run (opm catalog publish <catalog-dir> --dry-run, "member gate" row with 0 refused) checks the blueprint's identity only, and that the full render check is a module build with a component that embeds the wrapper, as in "Choose a blueprint". Verify: how a catalog author builds a module against a catalog they have not published yet. Check against: catalog_opm/AGENTS.md (Transformer fixtures), catalog_opm/docs/name-constraints.md (Fixtures that exercise a wrapper default), catalog_opm/src/blueprints/v1beta1/network_policy_attachment.cue, catalog_opm/.tasks/fixtures.sh, catalog_opm/docs/site/authoring/choose-a-blueprint.md (Check that it worked), cli/internal/publish/plan.go (renderCatalogGates) -->
