<!-- One sentence: this adds a new blueprint (a named composition of resources and traits, such as a stateless workload) to a catalog, so that module authors can start a component from one line and write its settings under one key. The reader needs it when the same combination of resources and traits recurs across modules and no blueprint in the catalog composes it. Say that a blueprint renders nothing itself: the transformers that handle its resources and traits render the component, selected by the matching label the blueprint answers. Say that nothing can demand a blueprint, so it has no fulfilment and no transformer of its own; a blueprint that needs a new workload type also needs a transformer, "Write a transformer". Check against: core/src/blueprint.cue, core/SPEC.md section 3.3, catalog_opm/opm/blueprints/v1beta1/stateless_workload.cue, catalog_opm/docs/site/authoring/choose-a-blueprint.md -->

## Before you begin

<!-- The reader must already have: a catalog to add the blueprint to, either a checkout of catalog_opm or their own catalog module (cue.mod/module.cue, identity/identity.cue and a catalog.cue that embeds core's #Catalog); every resource and trait the blueprint composes, defined and listed in that catalog (see "Write a resource" and "Write a trait"); the cue CLI at the version the catalog builds with (catalog_opm CI pins v0.17.1; Verify: the minimum version a reader needs); the opm CLI for the final check. The reader has read the concept page "Components and blueprints". Say that a trait from another CUE module cannot be attached beside a blueprint: the blueprint's spec is closed, and the trait's field fails with "field not allowed". Verify: whether a blueprint can compose a trait from another catalog module (the measured failure is for a trait attached beside the blueprint, not one it composes). Check against: catalog_opm/.github/workflows/ci.yml, catalog_opm/opm/catalog.cue, catalog_opm/opm/blueprints/v1beta1/network_policy_attachment.cue, core/src/component.cue (spec) -->

## Steps

<!-- The steps edit CUE files in the catalog source. The running example is stateless-workload: it composes one resource and five traits, answers the container resource's required workload-type key, and propagates each composed field with its guard at component level. stateful-workload is the example for a name constraint. Step 6 applies only when its condition holds, and step 12 applies only to catalog_opm; the step names say so. -->

1. File the blueprint under its apiVersion.
   <!-- The file goes in <module>/blueprints/<apiVersion>/<name>.cue with the package clause equal to the version segment (package v1beta1). The segment never enters the fqn, and publish refuses a blueprint filed flat or under any other segment. The contract levels are the same as for a resource: alpha promises nothing, and beta and GA members are additive-only. catalog_opm's five blueprints sit in opm/blueprints/v1beta1/, and no blueprints/v1alpha1 directory exists yet, so an experimental blueprint needs that directory and its own import alias in catalog.cue, grouped last. network_policy_attachment.cue in the v1beta1 directory is a test file, not a blueprint. Check against: catalog_opm/AGENTS.md (Version-segment filing, Listing), core/SPEC.md section 3.3 Constraints, catalog_opm/docs/site/reference/catalog-contract.md (Contract levels), catalog_opm/opm/catalog.cue -->
2. Declare the blueprint's identity.
   <!-- Show #<Name>Blueprint: c.#Blueprint & {metadata: {...}} with modulePath "\(id.kindPrefix.blueprints)/<apiVersion>", name in kebab case (stateless-workload), apiVersion, catalogVersion: id.Version, fqn "\(id.kindPrefix.blueprints)/<name>@<apiVersion>" and a one-line description. Write fqn with the interpolation on one line: task vet:listing builds the set of members it expects by grepping for that form. description is optional in core, but every catalog blueprint sets one. labels and annotations are optional and only describe; the five catalog blueprints set none. Never add fulfilment: nothing can demand a blueprint, and the closed definition refuses the field with "field not allowed". As for a resource, an fqn that disagrees with name or apiVersion passes cue vet and is refused by publish's member gate. Check against: core/src/blueprint.cue (metadata, the comment on fulfilment above composedResources), core/src/identity_package.cue (#CatalogMemberFQNGate), catalog_opm/opm/identity/identity.cue (kindPrefix), catalog_opm/.tasks/listing.sh, catalog_opm/opm/blueprints/v1beta1/stateless_workload.cue -->
3. List what the blueprint composes.
   <!-- composedResources lists the resources by definition ([res.#ContainerResource]); the stateful blueprint adds res.#VolumesResource. composedTraits lists the traits (tr.#ScalingTrait, tr.#RestartPolicyTrait, tr.#UpdateStrategyTrait, tr.#SidecarContainersTrait, tr.#InitContainersTrait). composedResources is required; composedTraits is optional. The lists are references only: the fields a module writes come from the schema (step 4), and the component carries the primitives because the wrapper embeds them (step 7). Verify: core/SPEC.md section 3.3 says composedResources must list at least one resource and that each composed trait must have a composed resource in its appliesTo, but core/src/blueprint.cue types the list as [...#Resource] and core/src/component.cue never reads appliesTo, so state both as requirements without naming a check. Check against: core/src/blueprint.cue (composedResources, composedTraits), core/SPEC.md section 3.3 Constraints, catalog_opm/opm/blueprints/v1beta1/stateless_workload.cue, catalog_opm/opm/blueprints/v1beta1/stateful_workload.cue -->
4. Write the schema under the blueprint's key.
   <!-- A separate #<Name>Schema in the same file reuses the schemas of what the blueprint composes: container: res.#ContainerSchema is required (no ?), and each composed trait is optional (scaling?: tr.#ScalingSchema; list-valued traits as sidecarContainers?: [...tr.#SidecarContainersSchema]). The blueprint's spec has exactly one field, named after it in camel case (stateless-workload becomes statelessWorkload), holding that schema: spec: statelessWorkload: #StatelessWorkloadSchema. Module authors write every setting under that key, composed traits included. Nothing composed appears at spec level until the wrapper propagates it (step 8). Check against: core/src/blueprint.cue (spec!), core/SPEC.md section 3.3 Constraints, catalog_opm/opm/blueprints/v1beta1/stateless_workload.cue (#StatelessWorkloadSchema), catalog_opm/docs/site/authoring/choose-a-blueprint.md -->
5. Answer the workload-type key.
   <!-- matchLabels: "core.opmodel.dev/workload-type": "<value>" on the blueprint. The container resource declares that key as required, with the values stateless, stateful, daemon, task and scheduled-task. Attaching the blueprint answers it and completes the component's matching identity, and the workload transformer whose requiredLabels carry the same value renders the component (the deployment transformer requires stateless, the daemonset transformer daemon, the cronjob transformer scheduled-task). Forks as conditions: if the blueprint renders to an existing workload kind, reuse its value and the existing transformers select it; if it needs a new kind, add the value to the container's enum in both places it appears (the resource's matchLabels and the #Container wrapper's metadata.labels), and write a transformer that requires it, following "Write a transformer". Verify: whether adding a value to the enum of the container resource at v1beta1 counts as additive (it widens a domain), and what each transformer that reads the value does with a new one (the hpa transformer falls back to Deployment for any value but stateful). Check against: catalog_opm/opm/resources/v1beta1/container.cue, core/src/component.cue (_matchLabelsFromPrimitives), catalog_opm/opm/transformers/deployment_transformer.cue, catalog_opm/opm/transformers/daemonset_transformer.cue, catalog_opm/opm/transformers/cronjob_transformer.cue, catalog_opm/opm/transformers/hpa_transformer.cue (_kind) -->
6. If the rendered workload's name is a DNS label, declare a name constraint.
   <!-- Set #nameConstraint: c.#NameType on the blueprint, as the stateful blueprint does: pod DNS (<sts>-<n>.<svc>) puts a StatefulSet's name in a DNS label position, which allows no dots and at most 63 characters. Otherwise leave it alone: the default accepts any name. Never guard on the slot's presence. Verify: stateful_workload.cue calls its constraint load-bearing, because on the blueprint path the container entry's own key is never answered, while core/SPEC.md section 3.3 calls it redundant with the container wrapper's computed constraint; confirm which before saying whether a new blueprint needs one. Check against: catalog_opm/opm/blueprints/v1beta1/stateful_workload.cue, catalog_opm/opm/resources/v1beta1/container.cue (#Container), core/src/blueprint.cue (#nameConstraint), catalog_opm/docs/name-constraints.md -->
7. Add the component wrapper.
   <!-- #<Name>: c.#Component & {...} beside the blueprint. It sets metadata: labels: "core.opmodel.dev/workload-type": "<value>", attaches the blueprint as #blueprints: (#<Name>Blueprint.metadata.fqn): #<Name>Blueprint, and embeds the wrapper of every composed resource and trait (res.#Container, tr.#Scaling, tr.#RestartPolicy, and so on). The label is not optional: the #Container wrapper declares that metadata label as required, and the hpa transformer reads the workload type from metadata.labels, not from matchLabels. The blueprint's own comment calls it a transitional duplicate until the kernel's matcher reads only matchLabels. Module authors embed this wrapper (bp.#StatelessWorkload), never the blueprint itself. Check against: catalog_opm/opm/blueprints/v1beta1/stateless_workload.cue (#StatelessWorkload), catalog_opm/opm/resources/v1beta1/container.cue (#Container), catalog_opm/opm/transformers/hpa_transformer.cue (_workloadType), catalog_opm/docs/site/authoring/choose-a-blueprint.md -->
8. Propagate the schema to the fields the transformers read.
   <!-- Transformers read spec.container, spec.scaling and the other flat fields, never spec.<camelName>. In the wrapper, re-declare spec with the blueprint's key and copy each required field: spec: {statelessWorkload: #StatelessWorkloadSchema, container: spec.statelessWorkload.container}. Copy each optional field with a guard at component level, outside the spec block: if spec.statelessWorkload.scaling != _|_ {spec: scaling: spec.statelessWorkload.scaling}. The wrong form puts that guard inside spec: {...}; for a struct- or list-valued field, cue rejects it with "field not allowed" (an evaluator regression from v0.17.0-alpha.2, still present in v0.17.1), so the hoisted form is load-bearing and must not be tidied away. Every schema field needs a propagation line, or a module's value is accepted and never reaches a transformer. Verify: #StatelessWorkloadSchema also carries securityContext, hostPid and hostIpc, which the blueprint does not compose, the wrapper does not propagate and no transformer reads under statelessWorkload; confirm whether that is a bug before pointing at the file as the model for this step. Check against: catalog_opm/opm/blueprints/v1beta1/stateless_workload.cue, catalog_opm/docs/cue-guard-closedness-workaround.md, catalog_opm/AGENTS.md (Repository Rules, CUE authoring pitfall), core/src/component.cue (_allFields, spec) -->
9. Write the doc comment.
   <!-- A new catalog member must ship a doc comment directly above #<Name>Blueprint: what it composes, what it renders to, what a value must satisfy, at most 6 lines. Rationale goes in a // WHY block above it, separated by one blank line. The generated INDEX.md takes the comment's first sentence, up to the first period, as the member's description. The five shipped blueprints carry no doc comment above the definition and show a blank description in INDEX.md; do not copy them. task docs:check fails a comment over 6 lines. Verify: catalog CI does not yet refuse a member with no doc comment (today it checks length only); state the rule as a requirement without naming a gate unless one has shipped. Check against: catalog_opm/AGENTS.md (Doc comments), catalog_opm/.tasks/doc-check.sh, catalog_opm/.tasks/generate-index.sh (extract_definitions), catalog_opm/opm/INDEX.md -->
10. List the blueprint in the catalog manifest.
    <!-- Add (bp.#<Name>Blueprint.metadata.fqn): bp.#<Name>Blueprint to the #blueprints map in catalog.cue, keyed by the fqn reference and never by a string literal, in alphabetical order. The value is the blueprint, not the wrapper: the wrapper declares no fqn and is not a member. The catalog stamps modulePath and catalogVersion on every entry, and a disagreeing authored value is a conflict. Check against: catalog_opm/opm/catalog.cue, core/src/catalog.cue (#blueprints), catalog_opm/.tasks/listing.sh, catalog_opm/AGENTS.md (Listing) -->
11. Add fixtures that build a component from the wrapper.
    <!-- In the blueprint's own package, not in transformers/ (transformers do not import blueprints, and should not start): _test<Name>: #<Name> & {metadata: name: "...", spec: <camelName>: container: {...}}, with each composed trait set. Pin what must arrive with a guard that forces evaluation, as network_policy_attachment.cue does with (len(_testNetPolOnStateless.spec.networkPolicy.policyTypes) + 0) & 2: a bare reference to an unresolved field is only incomplete, and cue vet accepts it. Pin what must not arrive with [if ... != _|_ {"leaked"}] & []. If a trait the blueprint does not compose must be attachable beside it, add an attachment fixture as network_policy_attachment.cue does for stateless and daemon. Verify: no shipped blueprint has fixtures of its own, and task vet:fixtures exports only transformer fixtures, so confirm which command a reviewer can rely on to exercise these. Check against: catalog_opm/opm/blueprints/v1beta1/network_policy_attachment.cue, catalog_opm/opm/transformers/network_policy_transformer.cue (the comment on the blueprint-attachment test), catalog_opm/.tasks/fixtures.sh -->
12. In catalog_opm, regenerate the index and run the checks.
    <!-- task generate:index regenerates opm/INDEX.md and k8s/INDEX.md, which lists the blueprint, its wrapper and its schema; task check runs format, vet, layering, listing, fixtures, index freshness and the doc-comment limit. task fmt:check diffs the git index, so stage the edits first. A new blueprint lands as a feat: commit, a minor release. Check against: catalog_opm/Taskfile.yml, catalog_opm/AGENTS.md (Build And Dev Commands, Commit conventions and release impact), catalog_opm/opm/INDEX.md -->

## Check that it worked

<!-- One command, from the catalog module directory: cue vet ./blueprints/<apiVersion>. Success is a silent exit with the step 11 fixtures in place. Say that the fixtures are what make it prove anything: vet never checks a hidden field for concreteness, so only a forced guard turns a field that never arrives into an error. Say that publish's dry run (opm catalog publish <catalog-dir> --dry-run, "member gate" row with 0 refused) checks the blueprint's identity only, and that the full render check is a module build with a component that embeds the wrapper, as in "Choose a blueprint". Verify: that a forced guard on a propagated field fails cue vet when the wrapper omits its propagation line (network_policy_attachment.cue proves attachment this way, not propagation), and how a catalog author builds a module against a catalog they have not published yet. Check against: catalog_opm/AGENTS.md (Transformer fixtures), catalog_opm/opm/blueprints/v1beta1/network_policy_attachment.cue, catalog_opm/docs/site/authoring/choose-a-blueprint.md (Check that it worked), cli/internal/publish/plan.go (renderCatalogGates) -->
