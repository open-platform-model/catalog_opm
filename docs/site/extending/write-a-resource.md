<!-- One sentence: this adds a new resource (something a component declares it needs, such as a set of namespaces or config maps) to a catalog, so that module authors can embed it in a component and a transformer can render it. The reader needs it when no resource in the catalog models the object their modules need. Say that every resource a component carries is a demand: a render refuses a component whose resource no transformer on the platform handles, so a resource ships with its transformer unless it is provider-fulfilled; that is the next page, "Write a transformer". Say that this page covers the abstraction catalog (opm/); a passthrough of a native Kubernetes kind goes in the raw catalog under k8s/resources/v1/, where apiVersion mirrors the upstream API version, the schema is an open wrapper, and there is no matchLabels and no name constraint. Check against: core/src/resource.cue, core/src/component.cue (the comment above #resources on resource demands), catalog_opm/AGENTS.md (Two catalogs, two key spaces), catalog_opm/opm/resources/v1alpha1/namespace.cue, catalog_opm/docs/name-constraints.md (k8s/) -->

## Before you begin

<!-- The reader must already have: a catalog to add the resource to, either a checkout of catalog_opm or their own catalog module (cue.mod/module.cue, identity/identity.cue and a catalog.cue that embeds core's #Catalog); the Kubernetes object the resource will render and its API version; the cue CLI at the version the catalog builds with (catalog_opm CI pins v0.17.1; Verify: the minimum version a reader needs); the opm CLI for the final check. The reader has read the concept page "Resources and traits". Link the page "Publish a catalog" for the catalog layout. Check against: catalog_opm/.github/workflows/ci.yml, catalog_opm/opm/identity/identity.cue, catalog_opm/opm/catalog.cue, core/src/catalog.cue -->

## Steps

<!-- The steps edit CUE files in the catalog source. The running example is the namespaces resource with its transformer: it is filed at v1alpha1, where a new abstraction starts, keys a map, declares a name constraint and has one transformer with golden fixtures. configmap.cue is the second example, for schema defaults. Steps 5 and 6 apply only when their condition holds, step 10 is skipped for a provider-fulfilled resource, and step 11 applies only to catalog_opm; the step names say so. -->

1. File the resource under its apiVersion.
   <!-- The file goes in <module>/resources/<apiVersion>/<name>.cue with the package clause equal to the version segment (package v1alpha1). The segment never enters the fqn. File a new abstraction at v1alpha1: alpha promises nothing and publish's compatibility gate skips it. Beta and GA members are bound by the additive-only rule (add optional or defaulted fields only; never remove a field, change a default or narrow a domain), and a breaking shape change is a new apiVersion file beside the old one. The level is per member and independent of the catalog's release version. A new version directory needs its own import alias in catalog.cue (catalog_opm has res for resources/v1beta1 and resa for resources/v1alpha1); a new file in an existing directory does not. Verify: whether a later shape change at alpha must be a new v1alpha2 file (write-a-trait.md says so) or may be an edit in place (the Catalog Contract says alpha may change or vanish between builds); no gate enforces either. Check against: catalog_opm/AGENTS.md (Version-segment filing), catalog_opm/docs/site/reference/catalog-contract.md (Contract levels, The additive-only rule), cli/internal/publish/compat.go (eligibleByPackage), catalog_opm/opm/catalog.cue, core/src/types.cue (#APIVersionType) -->
2. Declare the resource's identity.
   <!-- Show #<Name>Resource: c.#Resource & {metadata: {...}} with modulePath "\(id.kindPrefix.resources)/<apiVersion>", name in kebab case (a DNS label of at most 63 characters), apiVersion, catalogVersion: id.Version, fqn "\(id.kindPrefix.resources)/<name>@<apiVersion>", a one-line description, and labels "resource.opmodel.dev/category" (catalog_opm uses workload, config, storage, security and extension at v1beta1, and admission and cluster at v1alpha1). Say that metadata.labels only categorise: nothing selects on them. Write fqn with the \(id.kindPrefix.resources) interpolation on one line: task vet:listing builds the set of members it expects by grepping for that form, so a literal fqn is missing from it. Say who catches what: a modulePath that disagrees with apiVersion fails cue vet of the catalog package, because the catalog stamps modulePath on every listed entry; an fqn that disagrees with name or apiVersion passes cue vet and is refused only by publish's member gate. description is optional in core, but every catalog resource sets one. Check against: core/src/resource.cue (metadata), core/src/types.cue (#NameType), core/src/catalog.cue (#resources), core/src/identity_package.cue (#CatalogMemberFQNGate), catalog_opm/opm/identity/identity.cue (kindPrefix), catalog_opm/.tasks/listing.sh, catalog_opm/opm/resources/v1alpha1/namespace.cue -->
3. Write the spec schema.
   <!-- spec has exactly one field, named after the resource in camel case (config-maps becomes configMaps; namespaces stays namespaces), holding a separate #<Name>Schema definition in the same file. A second field, or a field with another name, is refused with "field not allowed". The schema must be expressible in OpenAPI v3. Two shapes exist: a keyed map whose key defaults into name (spec: namespaces: [KeyName=string]: #NamespaceSchema & {name: string | *KeyName}; never call the alias name, or the inner field shadows it), or a single object (spec: container: #ContainerSchema). Give a field that must end up concrete a default (immutable: bool | *false): a bare bool leaves the instance non-concrete, and it fails with "incomplete value bool". Mark required fields with !. If two options cannot be combined, make setting both a conflict error rather than a silently ignored field, as configmap.cue does for exactName and immutable. If the schema offers mutually exclusive forms, each disjunction arm must refuse the other arm's fields with other?: _|_. Say that cue vet passes a resource with no spec at all; the gap shows only when a component embeds it. Verify: whether to name cue eval -c -e '#<Name>Resource' ./resources/<apiVersion> as a check (the research measured that it catches a missing spec, but did not try it on a schema with required fields). Check against: core/src/resource.cue (spec!), core/SPEC.md section 2.1 Constraints, catalog_opm/opm/resources/v1beta1/configmap.cue, catalog_opm/opm/resources/v1alpha1/namespace.cue, catalog_opm/docs/struct-disjunctions.md -->
4. Decide what renders the resource.
   <!-- Two forks, written as conditions. If this catalog renders it, leave fulfilment at its default, "catalog", and write a transformer that requires it (step 10). If a platform provider implements it, set fulfilment: "provider" and ship no transformer, not even a stub: a stub is itself a provider, and the first real one would then be the second, which the render refuses as over-subscribed. Say what happens with no transformer: a resource has no advisory path, so the render refuses the component with an unresolved resource demand (0010:D28), where an unhandled optional trait is only a warning. Verify: no resource in either shipped catalog is provider-fulfilled yet (the two precedents are the v1alpha1 backup traits), so confirm the provider path end to end for a resource before describing it. Check against: core/src/resource.cue (fulfilment), core/src/component.cue (#resources), core/SPEC.md section 2.1 Constraints, catalog_opm/AGENTS.md (Provider-fulfilled members), catalog_opm/opm/traits/v1alpha1/backup.cue, library/opm/internal/renderstage/render.cue.tmpl (unresolvedResources), library/opm/errors/match.go -->
5. Declare a name constraint if the resource names a DNS object.
   <!-- If a transformer renders the resource into an object whose name lands in a DNS label position (a Namespace, a StatefulSet, a Service), set #nameConstraint to c.#NameType, as the namespaces resource does. Otherwise leave it alone: the default accepts any name. Never guard on the slot's presence. If the rule depends on what else the component carries, compute it on the wrapper's copy of the entry in list-index form, as #Container does: computed on the resource entry itself, it stays unresolved on the blueprint path. If the resource renders several exact names from its own map, also assert them on the wrapper (#Namespaces' _namespaceNamesFit), and never type the schema's name field itself: the type unifies into the *KeyName default and kills it. Check against: core/src/resource.cue (#nameConstraint), catalog_opm/docs/name-constraints.md (A computed constraint must resolve on every attachment path), catalog_opm/opm/resources/v1alpha1/namespace.cue, catalog_opm/opm/resources/v1beta1/container.cue -->
6. If transformers must select on it, declare a matching label.
   <!-- matchLabels is the resource's matching identity: a transformer's requiredLabels are compared with it, a component unions every attached primitive's matchLabels, and it is never rendered. A resource may declare a key as required ("<key>"!: <disjunction>) so that something else on the component, usually a blueprint, must answer it; #ContainerResource does this for core.opmodel.dev/workload-type, and it is the only catalog resource that does. A component cannot answer the key by writing it inline. Most resources declare no matchLabels, and the namespaces resource declares none. Check against: core/src/resource.cue (matchLabels), core/src/component.cue (_matchLabelsFromPrimitives, _matchLabelsAreDerived), catalog_opm/opm/resources/v1beta1/container.cue -->
7. Add the component wrapper.
   <!-- #<Name>: c.#Component & {#resources: (#<Name>Resource.metadata.fqn): #<Name>Resource}, right after the resource. This is what a module embeds: exp.#Namespaces in a component, then spec: namespaces: {...} (modules/cert_manager). Core does not require the wrapper, but every catalog resource ships one. Its kind is Component, so publish does not count it as a member. If the wrapper references spec, matchLabels or #names, declare that field first (spec: _), or vet fails with reference not found. Check against: catalog_opm/opm/resources/v1alpha1/namespace.cue (#Namespaces), catalog_opm/opm/resources/v1beta1/configmap.cue (#ConfigMaps), catalog_opm/docs/name-constraints.md (Lexical scope), cli/internal/publish/members.go (memberDiscriminators), modules/cert_manager/components.cue -->
8. Write the doc comment.
   <!-- A new catalog member must ship a doc comment directly above #<Name>Resource: what it is, what it renders, what a value must satisfy, at most 6 lines. Rationale goes in a // WHY block above it, separated by one blank line. The generated INDEX.md takes the comment's first sentence, up to the first period, as the member's description. Several shipped resources (namespaces, config-maps, container) carry no doc comment and show a blank description in INDEX.md; do not copy them. task docs:check fails a comment over 6 lines. Verify: catalog CI does not yet refuse a member with no doc comment (today it checks length only); state the rule as a requirement without naming a gate unless one has shipped. Check against: catalog_opm/AGENTS.md (Doc comments), catalog_opm/.tasks/doc-check.sh, catalog_opm/.tasks/generate-index.sh (extract_definitions), catalog_opm/opm/INDEX.md -->
9. List the resource in the catalog manifest.
   <!-- Add (resa.#<Name>Resource.metadata.fqn): resa.#<Name>Resource to the #resources map in catalog.cue, keyed by the fqn reference and never by a string literal. The value is the resource, not the wrapper. In catalog_opm, v1alpha1 members form the last group, under its comment, in alphabetical order. Listing is what makes the resource visible to a platform that subscribes to the catalog, including a provider-fulfilled one. Check against: catalog_opm/opm/catalog.cue, core/src/catalog.cue (#resources), catalog_opm/.tasks/listing.sh, catalog_opm/AGENTS.md (Listing) -->
10. Unless the resource is provider-fulfilled, write and list its transformer.
    <!-- Follow "Write a transformer". The transformer lists the resource under requiredResources, keyed by its fqn reference ((res.#NamespacesResource.metadata.fqn): res.#NamespacesResource, where namespace_transformer.cue imports resources/v1alpha1 as res), and imports the same resource package: the render unifies the component's copy of the resource with the transformer's. A transformer that names the resource only under optionalResources also counts as handling it. Its component fixture embeds the new wrapper (_testNamespacesComponent: res.#Namespaces & {...}). A resource alone needs no fixture of its own: task vet:fixtures exports only transformer fixtures. Check against: catalog_opm/opm/transformers/namespace_transformer.cue, library/opm/internal/renderstage/render.cue.tmpl (_bucketsResources, _resOutcome), catalog_opm/.tasks/fixtures.sh -->
11. In catalog_opm, regenerate the index and run the checks.
    <!-- task generate:index regenerates opm/INDEX.md and k8s/INDEX.md; task check runs format, vet, layering, listing, fixtures, index freshness and the doc-comment limit. task fmt:check diffs the git index, so stage the edits first. A new resource lands as a feat: commit, a minor release. Check against: catalog_opm/Taskfile.yml, catalog_opm/AGENTS.md (Build And Dev Commands, Commit conventions and release impact) -->

## Check that it worked

<!-- One command: opm catalog publish <catalog-dir> --dry-run. Success is the plan's "member gate" row reading "<n> members checked, 0 refused", and the "compat gate" row counting the new resource as alpha-exempt at v1alpha1, or as new at beta or GA, since no earlier build carried it (prerelease-exempt instead while the catalog's own version is a prerelease). Say that a catalog publish renders no component: a resource that no transformer handles passes every gate here and then refuses every render that attaches it, so the render check is the transformer's fixture export in "Write a transformer". Say that an "already holds <tag>" refusal only means the committed version is already published and is unrelated to the new resource; opm catalog version set moves it. Check against: cli/internal/publish/plan.go (renderCatalogGates), cli/internal/publish/catalog_gates.go (gateMemberFQN), cli/internal/publish/compat.go (eligibleByPackage, compatScan), cli/internal/publish/registry.go -->
